# Workflow rules

How agent workflows run on this project. Read this before writing a workflow script.

## Running several workflows at once

- Two workflows may run together only if their file sets do not overlap. Write the file list in each
  script's batch description, and check it against the other running workflows first.
- Shared hot files, never split across workflows: `src/bin/last_route/app/mod.rs`,
  `src/bin/last_route/net/world_sync.rs`, `src/bin/last_route/render/world_mesh.rs`, `src/bin/last_route/render/shader.rs`,
  `src/bin/last_route/world/route/furnished.rs`, `TODO.md`.
- Inside one workflow, batches run in order. Within a batch, agents run in parallel only when their
  files are disjoint.
- Agents do not run cargo while other workflows are editing. Each workflow ends with a read-only report.
  The lead runs the one build and test gate after every workflow has finished.

## Gates

- CI runs on this PC first with localci (see docs/LOCAL_CI.md). Run the Windows test job before a push.
- A push to GitHub is for the final check only, not to find failures.

- Build: `cargo build --bins --features server` and `cargo build --bin last_route` finish with zero warnings.
- Tests: `cargo test --locked --lib --bin last_route --bin lr_server --features server`.
  The one known failure is `generated_file_matches_generator`
  (prop_tables). Anything else that fails blocks the commit.
- Golden files under `tests/parity` are never regenerated by an agent. If a golden fails, the agent stops
  and reports the test name and the first difference.

## What agents may and may not do

- Agents do not edit `TODO.md`. The lead ticks items after the gate passes.
- Agents do not commit, push, restart a server, or touch a VPS. Those need the user's approval first.
- Agents do not print secrets: tokens, keys, `/etc/lastroute-rust/*.env` values. Use names only.
- A read-only agent says so in its script's `meta.description` and in its prompt.

## Writing the prompt

- Name the files the agent may edit, and the files it must not touch.
- Give the acceptance check: a test name, a build result, or a screenshot.
- Put the previous step's result into the next prompt only as a short excerpt.
- Keep replies short (under 150 words): files changed, test counts, what was not checked.

## Coding rules for workflow output

- Match the surrounding code's naming, comment density and idiom. Do not add a comment that restates the code.
- Gate test-only helpers with `#[cfg(test)]` rather than adding `#[allow(dead_code)]`.
- Keep the file's line endings. Several files are CRLF in the working copy; edit with the Edit tool or
  write CRLF back out. Do not change line endings in a diff.
- Do not change a schema name (`lr.region/1`, the save slot names) to add a key. Add an optional key.
- Keep Godot compatibility notes in the reply when a Rust-only change needs a Godot change.
- Every new public function in `lr_server` gets a unit test in its module.

## Reporting

- A workflow's final result lists per item: status (done, partial, blocked), the files touched, and the
  command that proved it.
- A blocked item is reported, not guessed around.

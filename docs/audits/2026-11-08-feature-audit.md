**Confirmed bugs**

- `game/ladder.rs:339` Walk-in mount on a top hatch bounces straight back out while forward is held. The runner stands on the step cell at the top of a downward shaft facing the hatch and holds W. ladder_walk_in (246-260) mounts at y_top with Phase::Mount. On the first Climb frame after 0.3 s, axis is positive and k.y >= y_top, so line 339 dismounts to the top exit, which is the same step cell. The runner is put back on the step cell while still holding W, and walk-in fires again, so the body loops between mount and dismount. The walk-in test (476-497) only asserts Phase::Mount and never runs the Climb frames, so it does not catch this. Fix: Make a walk-in mount wait for a fresh forward press before a top exit. Add a bool field to Climb (for example `fwd_armed`), set false in ladder_walk_in's start path (or pass a flag to Climb::mount), and set true on the first frame where axis <= 0.2. At line 339 require `fwd_armed` (`axis > 0.2 && k.y >= k.y_top && armed`). Also add a test that runs Climb frames with forward held after a walk-in mount and asserts the phase stays Climb, and a second test asserting the walk-in still dismounts after release and a fresh press. Do not change the turn-to-exit logic, which already prevents the loop.
- `game/ladder.rs:337` Held jump, not a fresh press, lets go of a ladder mounted from its bottom. The runner walks into an upward shaft from its foot (height 0, under LADDER_LET_GO_HEIGHT) while holding Space. Mount does not read jump. On the first Climb frame, c.jump is still held (Controls.jump is the held state; player.rs 466 derives jump_edge from it for hops), so line 337 starts a dismount to the bottom exit. The runner drops off at the foot the moment the climb starts. Ground hops use the fresh press (player.rs 466), so the ladder is inconsistent with them. Fix: In advance_ladder (ladder.rs ~line 315), before the match, derive the edge and keep the flag current while mounted: `let jump_edge = c.jump && !self.p.jump_prev; self.p.jump_prev = c.jump;`. Then change line 337 to `if jump_edge && k.height() <= LADDER_LET_GO_HEIGHT {`. Add a test: start the ladder with `jump()` held through the mount, then assert the phase stays Climb, and that a release followed by a fresh press dismounts.
- `game/level_stack.rs:164` Upper-floor head check uses 1.8 m body height, but the capsule is 1.90 m. BODY_HEIGHT is 1.8 (level_stack.rs:32) while PLAYER_HEIGHT is 1.90 (config/mod.rs:15), and the crouch capsule is shorter. For a standing body with feet at floor(owner+1) - 1.85, y + 1.8 is below the next floor, so the upper-level wall check at 164-170 is skipped. The capsule top (1.90) still pokes 0.05 m into the upper floor's storey, so a head can clip an upper-level wall or ceiling prop next to a flight. Fix: In game/level_stack.rs, delete `const BODY_HEIGHT: f32 = 1.8;` (line 32) and change line 164 to `if y_abs + crate::config::PLAYER_HEIGHT >= floor_y_of(owner + 1) {`. This is conservative for a crouched runner, whose capsule is shorter, so it may over-block a crouch under an upper wall. If hunters must keep their own height, pass the body height in as a parameter from the callers instead of using a single constant. Add a test: feet at floor(owner+1) - 1.85 under an upper-level wall cell must be rejected.

**Confirmed bugs**

- `game/items.rs:66` Stacked pickup loses items when merged into an existing stack. The player holds one battery in slot 1. A drop-hold of a 2-battery stack elsewhere leaves a floor pickup with n=2. Walking back and taking it calls grant(Battery, 2). The merge loop at L66-72 does s.n += 1 and ignores n, so the slot gets 2 and the pickup is marked taken. Result: one battery vanishes from the floor pile. The same loss happens for stims. Fix: In items.rs grant(), change the merge branch to add the requested count and only merge when the whole count fits, for example: `if s.item == item && s.n + n <= item.stack_max() { s.n += n; return true; }`. Then take_pickup only marks the floor pickup taken when all of its items fit. A partial fit falls through to the empty-slot branch, which keeps the full n, or returns false and leaves the pickup on the floor. Add a test in items.rs: a battery stack of 1 plus a floor pickup of 2 ends with 3 batteries and the pickup taken, or with the pickup left on the floor when the stack cannot take it all. Also check can_grant (L58) for the same off-by-count: it only checks for any room, so it can return true when the pickup will not fit.
- `game/interact.rs:637` Second body hiding takes a slot another hider already occupies. Two runners hide in locker L. A (front, slot 0) and B (beside, slot 1). A leaves, so OTHERS=[L] holds only B. Runner C enters: hiding_next_slot (L635-637) counts 1 other and returns slot 1, which is B's spot. hiding_full counts 2 bodies against capacity 2, so C is admitted and stands on top of B. Slot index is derived from a count, not from the occupied slots. Fix: Carry each other body's slot into interact.rs. Change OTHERS to Vec<(usize, u8)> (spot, slot), and have game/mod.rs:867-874 push (spot index, r.hide slot) instead of only the spot index. Keep hiding_occupants as a count over spot == i. Change hiding_next_slot to return the lowest slot in 0..hiding_capacity(i) not held by any OTHERS entry with that spot (fall back to the count only if no slot data is available). Add a test: set_other_bodies(vec![(li, 1)]), enter, and assert the new body is at slot 0 (front), not slot 1. Run the existing hiding_slots_are_front_then_beside test, which still passes because the first body still takes the front.
- `game/pipes.rs:371` New flows ignore the chunk's redirect valve outlet (suspected). A redirect valve in a sewer chunk is turned once (apply sets outlet via ev.turns % outlet_count = 1 on existing runs only). Later an Axe breach bursts another pipe in that chunk: open_burst (endless.rs L1026) calls start_flow, which hardcodes outlet 0 (L371, and L502 for flow valves). The new water comes out of outlet 0 while the redirect valve reads 1. Whether this is wrong depends on the intended Godot rule, which was not checked in this pass. Fix: Keep the chunk's current outlet in PipeNetwork (for example a BTreeMap<String, usize> keyed by flow_prefix(chunk)). Set it in apply() for EffectKind::Redirect (ev.turns % outlet_count, as now). Have start_flow and the flow-valve insert at L502 read that map (default 0) instead of hardcoding 0, deriving the chunk from the id via parse_valve_id. Add a test next to a_redirect_valve_moves_the_water_to_the_next_outlet: redirect once, then start_flow on the same chunk, then assert outlet == 1. Confirm the intended Godot rule before merging.
- `game/specialty.rs:343` Slot item silently removed when its hunter leaves, with no message. Glyra is out and the runner has the music box in slot 6 (not wound). Glyra leaves the run. Specialty::sync (L343-348) sets items[0]=None and clears a selected slot, and sync_specialty (mod L510-525) only announces Granted changes, so no toast or message says the box is gone. The player sees the box disappear with no explanation. Fix: In Game::sync_specialty (game/specialty.rs, match at L511-524), add arms for the removal, for example: Change::Removed(Kind::MusicBox) => self.say("MUSIC BOX // LOST WITH GLYRA"), and Change::Removed(Kind::Temperature) => self.say("TEMPERATURE ITEM // LOST"). Keep the existing items[i]=None removal. Optionally add a test next to the L723 assertion that checks a message was queued. Not built or run, per the read-only brief.

**Confirmed bugs**

- `app/mod.rs:1929` Quitting while downed saves the run as alive. The runner is downed with 30 s left on the 45 s timer and presses Esc, then Leave (pause Abandon). Pause is not gated by downed, and autosave('quit') (interact.rs:95-102) only checks report.is_some(). The checkpoint stores position and depth but no downed state, so Continue loads the runner standing up at that spot with no timer. Fix: In game/interact.rs autosave(), return false when the runner is downed as well as when the report exists: `if self.report.is_some() || self.downed.is_some() { return false; }`. This stops a downed quit from writing a standing save. Side effect: Continue then loads the last earlier checkpoint, not the downed spot, which is the intended tradeoff. Optionally also gate pause_allowed on the downed state so the menu cannot open while the 45 s timer runs. Add a test in game/revive.rs next to a_downed_runner_is_not_dead that asserts autosave("quit") is false while downed.
- `app/mod.rs:1743` Keyboard cannot reach the SPECTATE button on the run card. A dead runner in a multiplayer room uses Left, Right or Tab and Enter on the GAME OVER card. The focus only toggles between 0 and 1 (lines 1739-1743), so focus 2 (report.rs:352) is never selected. SPECTATE can only be chosen with the mouse. Fix: In mod.rs at lines 1739-1744, cycle focus over the number of visible buttons instead of toggling. Use `let n = if card.spectate.is_some() { 3 } else { 2 };` then Left does `*focus = (*focus + n - 1) % n;` and Right or Tab does `*focus = (*focus + 1) % n;`. Keep Enter and Escape as they are. The `card` binding is already in scope at line 1738.
- `game/endless.rs:575` Infinite population ignores data/progression.json streamed_base. On Nightmare with 0 relays, data/progression.json:13 sets streamed_base 2 and Progression::streamed_hunters would return 2. population() at endless.rs:565-576 returns 1 + 0 = 1, so the run starts with one hunter. Editing streamed_base has no effect on the live game. Fix: In src/bin/last_route/game/endless.rs, replace the body of `pub fn population(diff, relays)` (lines 565-576) with `crate::game::progression::Progression::load().streamed_hunters(diff, relays)`. Then delete the hardcoded step match. Keep the nyxie tests' use of population(diff, 0) working, since they compare against it. Add a test that population(Nightmare, 0) == Progression::load().gate(Nightmare).streamed_base so a future drift fails. Do not build or run tests in this read-only pass.
- `app/mod.rs:1677` Checkpoint saved in the last 2 s before death is lost on the card. A relay or checkpoint autosave happens 1 s before the runner is caught. finish_run (hunting.rs:693) clears the checkpoint file. last_save was last polled up to 2 s earlier, so it is None or stale, and the card shows RESTART ROUTE (can_respawn at line 1737) or respawns at an older checkpoint even though the newer save existed a second before death. Fix: Reload the checkpoint whenever an autosave actually happens, not on a timer. Add an autosave counter to Game (incremented in Game::autosave in game/interact.rs), and in app/mod.rs replace the save_poll block with: if g.autosave_count != seen_autosaves { seen_autosaves = g.autosave_count; if let Some(cp) = checkpoint::load() { last_save = Some(cp); } }. Read this before the frame's update runs, or the same-frame clear still wins. Keep the 2 s timer only if it is still needed for other writers. A simpler equivalent is to rebuild the Checkpoint from Game fields inside autosave and store it on Game, so death no longer depends on the disk copy.
